## Data and transaction design

`PlanningSlot` remains the aggregate root. Manual creation writes a draft `PlanningSlot` and a corresponding `EventInstance` within the existing request transaction. The server validates tenant ownership, distributions, date ranges and the PLANNER role. All new events begin in `PLANNED` regardless of the requested public visibility; public visibility becomes effective only after confirmation.

`released_at` is nullable for drafts and set on first confirmation. Migrating pre-existing confirmed slots sets the marker to their `updated_at` so older released events remain protected. The repository preserves that marker and refuses to reset the approval status. The delete method locks the DB row, checks `released_at` and `approval_status`, and hard deletes only drafts with DB cascades for dependent rows. Before deletion it removes associated invitation links and their unreleased target copies; already released target copies are cancelled and retained with stable identity. Deleting a target copy independently also removes its invitation link. The API performs a preliminary check for a helpful 409; the repository repeats it under lock to reject races. All saves (including updates) refresh and lock the persisted row before validating release invariants, preventing stale updates from withdrawing publication. The PATCH and bulk-approval handlers translate the resulting `ReleasedEventError` into HTTP 409 even if the conflicting publication happens after their initial read. The monthly retention task deletes only never-published rows and preserves released/cancelled events. The retention task invokes the repository aggregate deletion path per eligible event, so invitation links and related copies are reconciled, and concurrent publication is skipped without erasing the released row. Repository saves used by PATCH and bulk approval require an existing row and return HTTP 409 if a concurrent DELETE has removed the slot. Invitation removal reads and locks its target with a refreshed state before selecting cancellation or deletion.

## Cancellation and exports

An already released event is never deleted through the interactive API, nor by an external provider's `HARD_DELETE` flow. It becomes `CANCELLED` instead. ICS subscriptions continue publishing the same UID with `STATUS:CANCELLED`, revised `LAST-MODIFIED` and `SEQUENCE`. The events XLSX export keeps the row and exposes `Abgesagt`.

Unreleased events can be deleted without generating cancellation tombstones because they are not visible on public feeds. INTERNAL feeds can include drafts; deleting them is explicitly allowed and removes them from subsequent exports.

## Autogenerated drafts

Automatically generated drafts are physically deleted together with their dependent occurrences and assignments. A separate tenant-scoped `deleted_generation_keys` ledger stores `(district_id, generation_key)` before deletion. Both the eight-week Gottesdienst generator and the recurring PlanningSeries generators check this ledger before creating a slot. Series occurrences use a stable key derived from the series ID and the UTC planning date; legacy series slots with no key are recorded at deletion using that same identity. A durable `generation_key_detached` flag distinguishes deliberately reassigned series occurrences from legacy keyless events so deleting the former does not suppress the original recurring occurrence. Both series-generation implementations use the repository's uniqueness-safe SAVEPOINT insertion path to skip concurrent conflicts without discarding other generated slots. Manually authored drafts have no generation key and are simply deleted. The ledger survives ordinary event cleanup to avoid unwanted regeneration within the planning horizon.

## Security

Both endpoints require district-scoped PLANNER membership or a privileged superadmin. Congregations must belong to the requested district. The repository never trusts the UI's release flag.
