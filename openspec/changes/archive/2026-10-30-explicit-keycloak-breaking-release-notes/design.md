## Context
The repo already has release-specific upgrade-note files with required Betroffen/Vor/Nach sections. `scripts/publish_release_upgrade_notes.py` prepends these to an autogenerated release description, but does not distinguish mandatory breaking migrations.

## Decision
The standalone marker `**Breaking Change:**` identifies a compatibility-breaking operator note. The publisher switches only the top-level GitHub release note heading to a prominent BREAKING CHANGE heading; ordinary notes retain their original heading. Existing marker-based idempotency is unchanged. For #699 we require the marker and critical Keycloak manual actions in a committed file through a Docs CI unit test.

## Versioning trade-off
The existing 1.6.0 release train is not silently upgraded to a new major by this change. The explicit release runbook flags its SemVer compatibility exception for operator approval; a future release may make a deliberate Major decision separately.

## Tests
Regular note, breaking note, mixed notes, repeated publishing, missing Keycloak instructions and document validations. Coverage remains >80%.
